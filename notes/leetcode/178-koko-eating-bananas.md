# LeetCode 875 爱吃香蕉的珂珂

## 我的思路（50分钟）
- 前20分钟：想到二分查找速度，然后遍历 piles 计算总耗时来收缩边界。但担心这样时间复杂度会多乘一个 n，感觉会超时，且不知道初始边界怎么定
- 中间20分钟：看答案，发现就是这样做的——速度范围 [1, max(piles)]，每次取中间速度 mid，计算以该速度吃完所有香蕉的总耗时 hour，与 h 比较后收缩边界
- 后10分钟：照着思路写，但踩坑——返回值应该是遍历完后的边界值 left，而非计算过程中的 mid，调试了10分钟

## 代码
```python
class Solution:
    def minEatingSpeed(self, piles: List[int], h: int) -> int:
        left = 1
        right = max(piles)
        
        while left < right:
            mid = (left + right) // 2
            hour = 0
            for p in piles:
                hour += (p + mid - 1) // mid  # 向上取整
            
            if hour > h:
                left = mid + 1   # 速度太慢，吃不完，需要加速
            else:
                right = mid      # 速度够快，尝试减速
        
        return left
```

## 关键
- 二分对象：吃香蕉的速度 k（每小时吃几根）
- 速度范围：left = 1（最慢每小时吃1根），right = max(piles)（最快每小时吃一堆）
- 耗时计算：每堆香蕉耗时 ceil(p / mid)，用 (p + mid - 1) // mid 实现向上取整
- 收缩逻辑：
  - hour > h：当前速度太慢，吃不完，需要加速 → left = mid + 1
  - hour <= h：当前速度够快，尝试找更小的速度 → right = mid
- 返回值：left（循环结束时 left == right，即最小满足条件的速度）

## 教训
- 看到"最小速度/时间/代价使得条件满足" → 二分答案，先确定答案的范围，再验证可行性
- 向上取整技巧：(p + mid - 1) // mid 避免浮点数
- 返回值是 left 不是 mid：mid 只是中间试探值，最终收敛到 left
- 和 33/153 题对比：33/153 是在旋转数组中二分找值，875 是二分答案（速度）并验证可行性
